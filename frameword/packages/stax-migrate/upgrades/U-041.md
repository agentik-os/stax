# U-041: the shape router, and a gate so the catalogs cannot rot

TARGET: {{TARGET}}
REFERENCE: `stax-migrate shapes`, `frameword/packages/stax-migrate/shapes.json`,
DESIGN-SPEC.md "The shape router", `e2e/catalogs.spec.ts`

## DETECT

Three separate rots, all found in one pass on this repo. Check for each.

1. THE SHAPE GAP. The conversion doctrine maps a legacy screen to a panel TYPE
   and a NAVIGATION (drill, section, foot). Nothing tells the agent what the
   panel looks like INSIDE. Grep the mapping phase for the word "shape": zero
   hits means every domain surface will land on `data-panel/<entity>-table`,
   because the grammar can hold anything and a table is the least effort.
   Confirm at runtime: open five domain panels and count how many are grids. If
   it is five, the gap is real and visible.
2. THE UNREACHABLE CATALOG. A previous unit may have shipped a pattern catalog
   that no phase prompt ever mentions. `grep -l patterns templates/*.md` returning
   nothing means the knowledge exists and is unreachable, which is the exact
   failure that catalog was written to fix, one layer in.
3. DEAD REFERENCES. Every catalog reference is a promise that a live panel is
   there to copy. Drive all of them. A retired space leaves a placeholder that
   still renders a title, so a naive check passes: assert the panel body has
   CHILDREN, not just a title. Four references here pointed at spaces retired
   months earlier and every one of them looked fine to a title-only check.

## APPLY

1. BUILD THE SHAPE CATALOG from what the app ALREADY PROVES, never from
   imagination. Each entry: an id, `dataIs` (the trigger, phrased as what the
   data is rather than what the old screen was called), `shape` (the grammar,
   concrete enough to build), `proves` (the framework capability it displays),
   `antiPattern` (the specific mistake it prevents), and a live reference. If
   the app cannot demonstrate a shape today, it does not belong in the catalog.
2. KEY ON THE DATA, NOT THE SCREEN NAME. "Invoices page" tells you nothing;
   "append-only lines carrying a level" routes to `severity-log` immediately.
   The router works because an agent can describe unfamiliar data even when it
   cannot name the screen.
3. STATE THE ANTI-PATTERN IN EVERY ENTRY. `grid` must say "do NOT reach here
   first". Without it the catalog is a menu and the table is still the default.
4. WIRE IT INTO THE MAPPING PHASE as a MANDATORY step before any row is
   written: first `patterns "<screen name>"` for screens the framework already
   proves, then `shapes` for everything else, and record the chosen shape in the
   row's evidence so a reviewer can check it. A catalog nothing reads is worth
   nothing.
5. GATE BOTH CATALOGS. One e2e test drives every reference and fails on a panel
   whose body has ZERO children. A second asserts every reference uses the
   app's current URL form, so the catalog cannot quietly publish a URL style the
   app stopped emitting.
6. GATE THE CLI SURFACE TOO. Assert that every dispatched command appears in the
   help banner. Four commands hid here for months and they were the quality
   gates (verify, parity, theme, doctor), so an agent reading the banner
   concluded the framework had no design gate.

## VERIFY

- `stax-migrate shapes` lists every shape; `shapes --json` gives a machine-
  readable catalog; an unmatched query exits 1 with guidance, not silence.
- The e2e catalog gate passes: every reference opens a panel with a non-empty
  body. Break one on purpose and confirm the gate fails; a gate never seen red
  is not known to work.
- The CLI-surface test passes: no dispatched command is missing from the help.
- The mapping template names both commands, and a dry run of the mapping phase
  produces rows whose evidence column carries a shape.
- Count grids again on the same five domain panels. If the number did not move,
  the router was wired but not obeyed, which is a doctrine problem rather than a
  tooling one: say so plainly instead of shipping.
