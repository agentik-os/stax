# U-039: a money surface is a PANEL, not a table in a trench coat

TARGET: {{TARGET}}
REFERENCE: DESIGN-SPEC.md "The analytics surfaces" + the live Platform 05 Analytics space

## DETECT

The failure this unit exists to stop is a RATIONALIZATION, not a missing feature,
so detect it in prose before you detect it in code.

- Grep the domain for finance, trading, treasury, banking, close, P&L, blotter,
  portfolio, reconciliation. For each hit, look at the panel type it resolves to.
  Every one landing on `datatable` is a candidate defect.
- The tell in the copy: any sentence of the form "a financial dashboard is just
  tables, views and drills" or "the same engine, pointed at money". That sentence
  is how a generic grid gets shipped as a domain surface. It reads as doctrine
  and is actually an excuse: the grammar CAN express money, so nothing was built.
- The runtime tell: open the surface and ask what the user's first question is.
  A trader asks "did my orders fill and what did they cost", a treasurer asks
  "how much can I move today and what is unmatched", a CFO asks "where did we
  land against plan". If the panel answers none of those without the user
  scanning a grid column by column, it is a table wearing a domain name.

A table is CORRECT when the object genuinely is a row set the user edits: a
position book, a contact list, a task list. Keep those. This unit is about the
surfaces where the row set is the raw material, not the answer.

## APPLY

1. NAME THE QUESTION, THEN BUILD THE SHAPE. One panel answers one question with
   a purpose-built layout:
   - an execution blotter -> a FILL STREAM (time, side, symbol, size, price,
     venue, notional, realised P&L per line), a notional-by-venue breakdown, and
     a cost block (fees, blended bps, ordered against executed).
   - a treasury -> a CASH LADDER (one row per account, proportional bar, the
     reconciliation state as a dot, pending as a signed tail) plus an open-items
     block and a reconciliation rate.
   - a monthly close -> the P&L WALK (revenue, cost of revenue, gross margin,
     each opex line, EBITDA) with plan against actual on every row, and a cash
     and runway block.
2. DERIVE, NEVER TYPE TWICE. Totals, rates, gross margin, EBITDA and runway are
   COMPUTED from the line items in the module. A figure typed into two places is
   a lie waiting for the first edit. Make the panels reconcile: the treasury's
   closing cash divided by the CFO's average burn IS the runway the CFO prints,
   and it should be visibly the same number in both panels.
3. THE SIGN CARRIES MEANING, AND COSTS INVERT IT. A revenue line above plan is
   favourable; a COST line above plan is unfavourable. Compute
   `good = isCost ? delta < 0 : delta > 0` and colour from `good`, never from the
   sign of the delta. Getting this backwards is the single most common defect in
   a hand-built finance view.
4. NO CHART LIBRARY. Bars are divs with a percentage width against the row set's
   own maximum; the sparkline is an inline `svg` with `preserveAspectRatio="none"`.
   The whole point is that a rich money surface costs no dependency.
5. TOKENS ONLY. `--success`, `--destructive`, `--amber` for state; `--rule-1` for
   separators; `--secondary` for empty track. A plan ghost filled with
   `--secondary` VANISHES in dark: outline it with `inset 0 0 0 1px var(--rule-3)`
   instead. A negative actual gets a hatched fill so a loss is never read as a
   gain from bar length alone.
6. FOLD BY CONTAINER, NOT VIEWPORT. Each row is a grid; drop the low-value
   columns at `@container` breakpoints (order type and price first, then venue
   and timestamp) so the surface survives a narrow panel without wrapping.
7. THE FOOT STATES THE PANEL'S OWN TRUTH: a derived summary on the left, one
   accent verb on the right ("New order", "New payment", "Close the month").

## VERIFY

- `stax-migrate verify --url <app> --themes light,dark` passes on every new panel.
- Runtime, both themes: no computed colour equals a literal `rgb(0,128,0)` or
  `rgb(255,0,0)`; every state colour resolves through a token.
- Runtime: no value box is clipped. Assert `scrollWidth <= clientWidth + 1` on
  every money cell and that each row's right edge sits inside the panel's padding.
  A number column sized for "$1.2k" will clip "$10,709,250": reserve the width.
- Semantics, by hand: pick one cost line that came in UNDER plan and assert it
  renders favourable, and one revenue line UNDER plan and assert it renders
  unfavourable. If both are the same colour, rule 3 was not applied.
- Reconciliation: assert in a test that the figure shared between two panels is
  computed from the same source, not typed twice.
- The foot holds one line at every panel width down to the S floor (44px tall).
