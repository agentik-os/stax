# Stax for coding agents

Stax is a panels-inside-panels (Miller columns) framework. One mechanic: click
anything with depth and a panel opens to the RIGHT, and the parent stays. There
are no pages, no modals and no tabs. The whole UI derives from one serializable
`WorkspaceState`.

This file is the working contract for an agent editing a Stax app. Everything
below is checkable against the repo or against a running app. Paths are relative
to the repo root. Verified against `stax-migrate` 0.25.0.

The paste-ready master prompts (M1 to M10) are not in this file. They live in the
app (`#/prompts`) and are generated by `node frameword/scripts/gen-agents.mjs`.
That script REWRITES this file with the prompt dump, so do not run it unless you
intend to lose this contract.

Companion documents: [README.md](README.md) (what it is),
[PANEL-LOGIC.md](PANEL-LOGIC.md) (the engine grammar),
[DESIGN-SPEC.md](DESIGN-SPEC.md) (the pixel contract, the SSOT for design),

## Add a panel

Five edits, in this order. Nothing else is required.

1. `src/domain.ts`: add the node. The key is `namespace:name`
   (`"an:blotter"`), and it carries `panelType`, `title`, `eyebrow`, `subtitle`,
   and optionally `children`, `meta`, `footActions`.
2. `src/domain.ts`: add the key to its parent's `children` array, or to a space's
   `rootKey` subtree. That is what makes the row drillable.
3. `src/App.tsx`: add `panelType: { size: "S" | "M" | "L" | "XL" | "XXL" }` to
   `REGISTRY`. Width belongs to the kind, never to the instance, and never to a
   hardcoded style.
4. `src/App.tsx`: add one line to the body render switch,
   `{p.target.panelType === "yours" && <YourBody />}`. Heavy modules go behind
   `<Suspense>` (see `blocklive` and `canvasedge` in the same block).
5. Foot actions go in the registry the foot, the palette and `window.stax` all
   read. The foot is the only action zone in a panel.

The slug follows automatically: `an:blotter` becomes `#/analytics/blotter` with
no further work, because `slugs.ts` builds its index from `DOMAIN`.

## Address it in a URL (the slug contract, 0.25.0)

A Stax link is a thing people paste into Slack, so it reads like a path someone
could have guessed:

```
#/analytics/blotter          not  #/pf-analytics/section~sec:pf-analytics/anblotter~an:blotter
#/crm/acme/jo/refonte        four panels, one URL
#/console/keys               the API keys panel inside the console space
```

The engine stays domain-free. `encodeLocation(state, codec?)` and
`decodeLocation(encoded, codec?)` in `panels-core/src/index.ts` take an OPTIONAL
`SlugCodec`; the app supplies the meaning. With no codec the old `type~key` form
is produced, unchanged, so adding a codec is never a breaking change.

```ts
export interface SlugCodec {
  slug(target: PanelTarget, spaceId: string): string | null;  // null falls back to type~key
  target(slug: string, spaceId: string): PanelTarget | null;
  root?(spaceId: string): PanelTarget | null;                 // dropped from the URL
  spaceSlug?(spaceId: string): string | null;                 // pf-analytics -> analytics
  spaceId?(slug: string): string | null;
}
```

Wire it in one place: `<WorkspaceProvider registry={REGISTRY} urlSync="push"
slugCodec={slugCodec}>` (`App.tsx` line 210). The provider threads it to all
three decode sites and the single encode site.

**The four naming rules** (implemented in `slugs.ts`, read it before changing
anything):

1. A space is named by its PUBLIC slug, not its internal id. `pf-analytics`
   becomes `analytics`, `pf-console` becomes `console`, `ana-poss` becomes
   `possibilities`. Anything already human stays as it is (`crm`, `laws`).
2. The space ROOT is never written. Opening a space already opens it, so encode
   drops the root segment and decode puts it back. `#/analytics/blotter` opens
   two panels.
3. A node's slug is its resource key with the namespace stripped:
   `an:blotter` becomes `blotter`.
4. On a collision the PUBLIC surface wins the bare word and the losers keep a
   qualified form. `pf:keys` takes `/keys`; `imp:keys` becomes `/imp-keys`. The
   ranking is the explicit `NS_RANK` array, never iteration order, so a shared
   link cannot change meaning between builds. A slug that is only digits is
   never awarded, because `/1` addresses nothing a human can read.

**Three forms decode, and they mix inside one URL:** a bare slug (needs the
codec), an explicit `type~key` segment (never needs it), and the legacy
percent-encoded JSON. Mixing has to be legal per segment, because a runtime
resource (a data row, a note created five seconds ago) is not in the static
domain and must fall through. Old links do not rot, and they self-normalise: open
the long form and the address bar rewrites itself to the short one.

**Degrade, do not fail.** An unresolvable slug stops the walk and opens what did
resolve, so a renamed leaf lands the visitor in the right space instead of on an
empty screen.

Two traps the reference codec sets, both observed at runtime:

- Its index is GLOBAL, not per space. `slugs.ts` ignores the `spaceId` argument,
  so `#/improvements/keys` opens the console's API keys panel inside the
  improvements space. Scope the index per space if that is wrong for your app.
- Only spaces listed in `SPACES` get an implied root. The system spaces (data,
  notes, tasks, canvas) are not, so `#/data` alone resolves to nothing and the
  address is `#/data/data`.

The contract is tested in `frameword/apps/crm-specimen/e2e/urls.spec.ts`
(byte-for-byte round trip, implied root, self-normalisation, mixed segments,
unknown slug, the collision pair). The backward-compatibility proof is that the
pre-existing suite, which navigates with the old format, still passes unchanged.

## The head layouts (0.22.0)

A panel's identity is a DATA plan, not a hardcoded render. `headLayouts.ts`
exports the `HeadLayout` union, the `HEAD_LAYOUTS` catalog and one pure function
`headPlan(layout, ctx) -> HeadPlan`. The Panel renders the plan and decides
nothing on its own, so a new treatment is a row in the table, never a fork of the
component.

Ten treatments ship. `dense-bar` is the default (`DEFAULT_HEAD_LAYOUT`), density
defaults to `compact`:

`dense-bar` (default, bar carries glyph + title + live numbers, body is pure
content, reclaims 89px) · `echo` (a drill never repeats the row that opened it,
97) · `no-subtitle` (58) · `bar-title` (97) · `focus-only` (97) ·
`scroll-collapse` (97) · `first-run` (97) · `spine` (a vertical rail, 122, costs
18px of width) · `density` (dense-bar plus cozy/compact/dense rhythm) ·
`editorial` (the original eyebrow + serif title + description, 0).

Context in: `isRoot, isRef, focused, echoesParent, scrolled, seen, compact,
hasSubtitle`. Plan out: `barEyebrow, barGlyph, barTitle, barMeta, bodyTitle,
bodySub, info, spine, titleScale`.

Binding laws: a panel ALWAYS states its identity somewhere; the foot stays the
only action zone; the bar folds by priority under 640px (numbers first, eyebrow
next, title never) and the fold is a CONTAINER query on `.panel`, never a
viewport media query; the bar's live numbers are derived (row count, first KPI,
child count) and never authored; the root's bar title keeps the serif voice at
about 1.16x body so rank does not collapse.

The user picks a treatment in the appearance panel (`App.tsx`, `HEAD_LAYOUTS`
near line 2036); the choice is device-local, like theme and zoom.

## Do not build a table in a trench coat (0.24.0)

This is the mistake an agent makes on a domain surface. The data grammar CAN hold
trades, cash and a P&L, so it is tempting to ship three grids and call it a
financial dashboard. The grammar being capable is not the same as the surface
being built. Name the user's first question, then build the shape that answers
it.

| Surface | The question | The shape |
|---|---|---|
| Position book | what do I hold | a TABLE, genuinely: a row set the user edits |
| Execution blotter | did my orders fill, what did they cost | a fill stream + notional by venue + a cost block |
| Treasury | how much can I move, what is unmatched | a cash ladder with a state dot + open items + a rate |
| Monthly close | where did we land against plan | the P&L walk, plan against actual, then cash and runway |

Three laws keep such a surface honest:

1. **Derive, never type twice.** Totals, gross margin, EBITDA, fill rate and
   runway are computed from the line items. Two panels sharing a figure compute
   it from one source: the treasury's closing cash over the CFO's average burn IS
   the runway the CFO prints. A number typed in two places is a lie waiting for
   the first edit.
2. **The sign carries meaning, and costs invert it.** A revenue line above plan
   is favourable, a cost line above plan is not. Compute
   `good = isCost ? delta < 0 : delta > 0` and colour from `good`, never from the
   raw sign (`AnalyticsApp.tsx`, `CfoBody`). Getting this backwards is the single
   most common defect in a hand-built finance view.
3. **Tokens carry state, and dark is the harder case.** `--success`,
   `--destructive`, `--amber` for state, `--rule-1` for separators. A plan ghost
   filled with `--secondary` VANISHES on a dark canvas, so outline it with
   `inset 0 0 0 1px var(--rule-3)`. A negative actual gets a hatched fill so a
   loss is never read as a gain from bar length alone.

Two more that bite in practice: reserve the number's width (a column sized for
`$1.2k` clips `$10,709,250`, let the bar yield and never the digits), and fold by
`@container`, not viewport, so a narrow panel drops columns instead of wrapping.
No chart library: bars are divs with a percentage width against the row set's own
maximum, and the sparkline is an inline `svg` with `preserveAspectRatio="none"`.

Working reference: `frameword/apps/crm-specimen/src/AnalyticsApp.tsx`
(`BlotterBody`, `TreasuryBody`, `CfoBody`, `AnalyticsFoot`), live at
`#/analytics/blotter`, `#/analytics/treasury`, `#/analytics/cfo`.

## Do not improvise a screen the framework proves (0.23.0)

Before designing a SaaS admin screen, ask the catalog:

```sh
node frameword/packages/stax-migrate/index.mjs patterns "api key"
node frameword/packages/stax-migrate/index.mjs patterns --json     # all 20
```

It prints the panel type, the grammar that makes it Stax, and a live reference
link. Real output:

```
stax patterns · "api key"

  API keys / tokens page (create, reveal once, roll, revoke)
  target  pfkeys: a .dt of keys with masked secrets, a REVEAL-ONCE dialog on
          creation (the secret is never re-shown), roll and revoke as row
          actions, the row drills to the key's panel
  live    /#/pf-console/section~sec:pf-console/pfkeys~pf:keys
```

An unmatched screen exits 1 and sends you to the view grammar rather than letting
you guess. The 20 rows cover API keys, team and invitations, projects, the
billing hub (sub-pages as drills, never tabs), usage metering, rate limits, log
stream, service health, security posture, data controls, asset library,
playground, terminal, chat, realtime, integration hub, and four report shapes.

Two caveats before you trust a printed link. The catalog still prints the LEGACY
long URL form; it resolves and self-normalises to the short one, so
`/#/pf-console/section~sec:pf-console/pfkeys~pf:keys` lands on `#/console/keys`.
And the four report rows (funnel, sources, mrr, forecast) point at the retired
`ana-overview` and `ana-revenue` spaces: they open empty placeholder panels. Use
the grammar in those rows, not the link.

## Auditing Stax conformance

`node $CLI audit <transfer|stax|cohesion> [dir] --url <live>` runs the real
gates and writes `.stax-audit/<mode>-evidence.json`. The forensic half is the
`staxaudit` skill. `unreachable` is an ABORT and not a score; `not applicable`
is not a failure. An audit cannot assert more than it ran: if PASS phases
outnumber captured commands, confidence caps at medium.


## The gates

Run these, in this order, and show the output. A green build with a red console
is not shipped.

```sh
# 1 · unit gate: the engine laws + the CLI cases (122 tests, 0 fail)
cd frameword && bun run test

# 2 · the committed regression suite (50 specs) against a running app
cd frameword/apps/crm-specimen && BASE=http://localhost:5799 bunx playwright test -c e2e/playwright.config.ts

# 3 · the design-law scan on the real page, both themes
node frameword/packages/stax-migrate/index.mjs verify --url http://localhost:5799 --themes light,dark

# 4 · adoption health on a target project (contract, pending units, token drift)
node frameword/packages/stax-migrate/index.mjs doctor <dir>
```

Green looks like: `122 pass 0 fail`, `50 passed`, and
`PASS: every scanned view honors the design laws.`

Do NOT run bare `bun test` from `frameword`: it sweeps the six Playwright e2e
specs into bun's runner, which cannot execute them, and reports 6 false failures.
`bun run test` is the scoped script.

For a whole-app migration the CLI is the program, not a prompt:

```sh
node frameword/packages/stax-migrate/index.mjs init <dir> --level full   # or standard | starter | shell
node frameword/packages/stax-migrate/index.mjs next <dir>                # the current phase brief
node frameword/packages/stax-migrate/index.mjs run  <dir> --agent claude # drive ONE phase
node frameword/packages/stax-migrate/index.mjs done <dir>                # validate the exit gate, then advance
node frameword/packages/stax-migrate/index.mjs status <dir>              # three coverage matrices
node frameword/packages/stax-migrate/index.mjs contract <dir>            # the honesty check (exit 1 on breach)
```

An app ALREADY on Stax never re-migrates. It pulls the versioned catalog instead:

```sh
node frameword/packages/stax-migrate/index.mjs upgrade <dir>              # applied vs pending (U-001 to U-040)
node frameword/packages/stax-migrate/index.mjs upgrade plan U-040 <dir>   # print one unit's DETECT / APPLY / VERIFY
node frameword/packages/stax-migrate/index.mjs upgrade run  <dir> --agent claude
node frameword/packages/stax-migrate/index.mjs upgrade done U-040 <dir>   # the OPERATOR records it, never the agent
```

## Drive a running workspace

`window.stax` exposes the state and every intent, and it is the same action
registry the foot and the palette read.

```
getState()                 the full serializable WorkspaceState
path()                     the current thread as resourceKeys
find(text)                 [{key, title}] fuzzy title matches
open(key)                  deep-link any resource (the chain is rebuilt)
openSpace(spaceId)         start a space thread
actions(panelId?)          the focused panel's registry actions [{id,label,kind}]
act(actionId, panelId?)    run one
pin() unpin() close() focus(id) undo() redo()
```

Read `getState()` before acting, prefer `act()` over synthetic clicks, and never
fabricate an id: ids come from `getState()` or `find()`. The agent drawer's slash
commands are this bridge, spoken.

## The laws, short form

1. Opening a space replaces the active thread; pinned references ride across it.
2. One action zone per panel, the foot. Never a floating button.
3. Parents stay visible, depth reads left to right, the palette goes anywhere.
4. State is a serializable list; the URL, the crumbbar and the agent context all
   derive from it.
5. Tokens only. Change the accent and the whole system follows.

Every claim in a report carries evidence: a file:line, a command's raw output, or
a screenshot. Prose without evidence is a fail.
